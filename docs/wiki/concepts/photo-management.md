# Photo Management

## Model (since 2026-11-16)

A gallery is one Firestore document in `galleries` with its images embedded. The image bytes are static repository files. This replaced the flat `images` collection plus Firebase Storage uploads ([Decision 0016](/decisions/0016-gallery-management.md)).

## Gallery document schema (Firestore `galleries`)

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Firestore document id — not stored in the document; mapped explicitly |
| `name` | string | Gallery title, shown uppercase in the public grid |
| `slug` | string | Public URL segment; `^[a-z0-9]+(-[a-z0-9]+)*$`, unique |
| `description` | string | Intro text, admin-only for now |
| `displayOrder` | number | Position in the public grid |
| `coverImageUrl` | string | Cover path or URL; falls back to the first image when empty |
| `images` | array | Embedded `GalleryImage[]`, the authoritative order |
| `createdAt` | timestamp | Server timestamp on create |
| `updatedAt` | timestamp | Server timestamp on every write; rules require it |

Each `GalleryImage`:

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | UUID generated by the admin for stable drag-and-drop keys |
| `url` | string | `/galleries/<file>` path or a full URL |
| `title` | string | Caption shown on hover and in the lightbox |
| `alt` | string | Accessible description; falls back to the title |
| `ratio` | string | CSS aspect ratio (default `3/2`) so the feed reserves space |
| `order` | number | Mirrors the array index; normalized on every save |

The TypeScript mirror is `Gallery`, `GalleryImage` and `GalleryDraft` in `src/types/gallery.types.ts`.

## Image files

- Location: `public/galleries/` (single directory, served from the site origin as `/galleries/<file>`).
- Format: WebP or JPEG, ~1600 px on the long edge, pre-generated by the owner.
- No upload pipeline, no Storage bucket, no Blaze requirement for images.
- Adding a photo = commit the file, then add its path in the admin; deployment publishes it.

## Ordering

- Gallery order: `displayOrder`, edited directly or by drag-and-drop on `/admin`.
- Image order: the `images` array plus the mirrored `order`; drag-and-drop inside the editor, persisted atomically with the gallery.
- Public queries: `orderBy('displayOrder')` for the grid; the document array for the feed.

## Visibility and deletion

- There is no soft-delete flag in the new model: a gallery is published or deleted.
- Deleting a gallery removes the document only; files stay in the repository and must be removed manually.
- Hidden drafts are not supported yet. A future `isVisible` field would be a schema addition.

## Legacy model (removed 2026-11-16)

The old `images` collection (`name`, `url`, `metadata`, `collection`, `isFavorite`, `isLatestWork`, `isCoverImage`, `isVisible`, `order`, `createdAt`) and the `ImageUpload` screen were deleted. `storage.rules` is gone too. Any documents left in `images` are unreachable because `firestore.rules` falls through to the catch-all deny.

The previous bug where `react-firebase-hooks` 5.1.1 ignored `idField` is no longer relevant: the new store reads documents directly and maps ids itself.

## Static fallback content

Until the owner seeds `galleries`, the public site keeps rendering the captured CDN dataset:

- `src/data/collections.data.ts` — 9 covers and optional placeholders.
- `src/data/collections.photos.ts` — 89 photos (24 for `01-favorite`) with Adobe CDN URLs, Italian captions and aspect ratios, captured 2026-10-30.
