# 0026 — Accept either Firebase secret and keep three workflows

## Context

The first production deploys failed. `Deploy` run `44951483231` on `main` reached **Deploy Firestore rules** and stopped with `403 Permission denied to get service [firestore.googleapis.com]` for project `alessandrotorri-it`. Because the rules step runs before Hosting, nothing was published and `https://alessandrotorri-it.firebaseapp.com/` answers "Site not found".

Two secrets were configured: `FIREBASE_SERVICE_ACCOUNT` (2026-11-21T07:41Z), used by every failed run, and `FIREBASE_SERVICE_ACCOUNT_ALESSANDROTORRI_IT` (2026-11-21T21:16Z), generated by `firebase init` for this project. The workflows only read the first one.

Separately, `firebase init` on `main` committed `.github/workflows/firebase-hosting-pull-request.yml`, `public/index.html` (the Firebase welcome page) and `skills-lock.json`. `development` never received them.

## Decision

1. **One credential, two accepted names.** `deploy.yml` and `preview.yml` resolve the job-level variable as `secrets.FIREBASE_SERVICE_ACCOUNT_ALESSANDROTORRI_IT || secrets.FIREBASE_SERVICE_ACCOUNT`. The project-specific name wins because it is the key generated for this project; the generic name stays as the compatible fallback and can become canonical again by fixing its IAM roles.
2. **Validate before deploying.** The production workflow fails with a clear message when neither secret is set, refuses a credential that is not JSON or lacks `client_email`/`private_key`, and warns when the key's `project_id` differs from the target project. The key's content is never printed; only `client_email` is logged.
3. **Explicit target.** `FIREBASE_PROJECT_ID` is set once at workflow level as `vars.FIREBASE_PROJECT_ID || 'alessandrotorri-it'` and passed to both the CLI and the Hosting action; `channelId` stays `live`.
4. **Three workflows, no generated ones.** `ci.yml` (pushes to `development`/`main`, pull requests to `development`/`main`), `preview.yml` (PRs to `development`/`main`) and `deploy.yml` (`main`, `v*` tags, manual). Any `firebase-hosting-*.yml` file is deleted when it appears.
5. **Rules before Hosting.** Unchanged from [Decision 0025](/decisions/0025-release-v1-and-ci-cd.md): a rules failure stops the release instead of shipping a client that the deployed rules reject.
6. **Plan of record stays in the wiki.** The root `IMPLEMENTATION_PLAN.md` already existed from the v1.0.0 loop and was rewritten for this fix, but the analysis, decision and playbook live in the bundle ([Decision 0004](/decisions/0004-wiki-layout.md)).
7. **`main` is reset, not patched.** `df2aea2` on `main` (generated workflow, `public/index.html`, `skills-lock.json`, `.gitignore` touch) is not reachable from `development`, so a PR into `development` cannot delete it. Because it was the only commit by which `main` was ahead and it carried nothing else, `main` was force-updated to the `v1.0.0` commit (`59f87e3`) on 2026-11-21. `public/index.html` must never be committed again: Vite copies `public/` into `dist/`, and a placeholder entry page has no place in the build input.

## Consequences

Positive:

- The verified working credential is picked up without deleting or renaming secrets.
- A wrong or missing credential fails in seconds with an actionable message instead of a 403 deep inside `firebase-tools`.
- The project id and channel are explicit and auditable in one place per workflow.
- No duplicate deploy workflows can race each other.

Negative:

- The precedence is implicit: fixing `FIREBASE_SERVICE_ACCOUNT` alone keeps the project-specific secret in use until it is removed.
- `checks: write` was added to `deploy.yml` for the Hosting action; the token stays read-only for repository contents.
- GitHub masks secret values in logs, so `client_email` is the only identity evidence in a failing run.
- The `main` reset was a one-off history rewrite; nothing in CI prevents a future `firebase init` artifact from being committed again.

## Alternatives rejected

- **Delete `FIREBASE_SERVICE_ACCOUNT` and use only the generated name.** Rejected: it breaks every document that names the generic secret and makes rotation harder.
- **Keep the generic secret first.** Rejected: it is the one that returns 403 on `firestore.googleapis.com` today.
- **Split the rules into a separate workflow.** Rejected: rules and client must ship together ([Decision 0025](/decisions/0025-release-v1-and-ci-cd.md)).
- **Point Hosting at `public` as the source prompt assumed.** Rejected: `dist` is the Vite output and the shipped site; `public/` only holds static assets copied into it.
- **Write `IMPLEMENTATION_PLAN.md` at the root.** Rejected: violates the bundle layout.
